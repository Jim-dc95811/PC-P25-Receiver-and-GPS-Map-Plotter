The Audio-Capture Path

Getting the radio's audio into the decoder, cleanly — an engineering reference

Claude McNally's PC P25 Receiver & GPS Map Plotter  ·  v2.6  ·  2026‑11‑27

This document explains, end to end, how the receiver gets the radio's detector audio off the sound card and into the decoder without Windows altering it — why that matters, the audio‑level science behind it, and the four separate bugs that stood between "we asked for exclusive mode" and "exclusive mode actually engaged." It is written for a radio engineer who is not a Windows‑audio specialist: every term is explained where it first appears, and there is a glossary at the end.

1 · What this subsystem does, and where it sits

The receiver turns a P25 radio's detector (discriminator) audio — the raw demodulated baseband, not the speaker audio — into decoded GPS positions and voice, plotted on an offline map. The very first link in that chain is the one this document covers: reading the audio samples off the USB sound card. Everything downstream (the C4FM symbol recovery, framing, FEC, the IMBE voice decode) depends on those samples being a faithful copy of what the radio produced.

The physical path:

radio detector output  →  USB sound card (line/mic input)  →  Windows  →  Python (sounddevice)  →  decoder
  (analog baseband)        (ADC: analog → 16‑bit samples)    ( ??? )      (our capture code)     (DSP)

The whole fight in this document is about that ??? box — what Windows does to the samples between the sound card's analog‑to‑digital converter (ADC) and our program — and how to make it do nothing.

2 · Does the audio level matter? — the science that shaped the design

Before touching Windows, we answered a more basic question the honest way: does the input level affect how well the signal decodes? If it did, the receiver would need a level meter and a calibration step. If it didn't, all of that could be deleted.

Two facts about the signal:

  • The level is hardware‑fixed. The radio's detector output is a fixed amplitude, and the sound card's ADC turns it into samples at a fixed scale. Nothing the operator does changes it — short of the Windows slider, which is exactly the variable we want to remove.
  • The hiss‑to‑signal ratio is a fixed ~3:1. Between transmissions the open squelch delivers broadband receiver noise ("hiss"); a C4FM packet is quieter than that hiss by a fixed ratio (FM quieting). That ratio is a property of the radio's design and varies only a few percent across units — component tolerance.

We then measured it directly. Using real STD 153 (ITU‑T O.153) pattern recordings captured at eight RF levels from −50 to −120 dBm, we swept the digital level from near‑zero to full scale and scored the bit error rate (BER) at each step. The result is a flat bathtub with one steep wall:

Finding: audio input level does not affect decode BER. The error floor is set by RF signal‑to‑noise ratio, not by level. Level only matters in one way — stay off the clip wall. Past roughly 70% of full scale the hiss peaks begin to clip, and then BER rockets from near‑zero to 40–50%. Below that wall, a huge range of levels all decode identically. (The left/quantization wall is buried ~70 dB down by 16‑bit depth, so it never bites.)

This is why the receiver ships with no level meter and no calibration step. The one real risk — clipping — is removed structurally by capturing in exclusive mode (next sections), which takes the Windows level slider out of the path entirely so the fixed hardware level lands mid‑bathtub and can't be driven into the wall. "A person can't go wrong."

The clip wall is not academic. During this very session, with the receiver mistakenly running in shared mode, turning the Windows mic level to 100% drove the hiss into clipping and killed the decode; turning it back down restored it instantly. That behavior was the smoking gun that exclusive mode was not actually engaged — see §5.

3 · What Windows does to microphone audio (shared mode)

By default, every app on Windows shares the sound card through the Windows audio engine. The engine is a software mixer, and for a capture device it can apply, in order, before your app ever sees a sample:

  • A level/volume multiply — the "Microphone" slider in Sound → Recording → Levels. At 100% it can amplify past the card's natural scale, which is how shared mode clips our hiss.
  • Automatic gain, "enhancements," noise suppression, echo cancellation — voice‑oriented processing that is helpful for a headset and poison for a C4FM baseband.
  • Resampling to the engine's shared mixing format.

This path is called WASAPI shared mode (Windows Audio Session API). It is the right default for ordinary apps and the wrong thing for us: we want the exact samples the ADC produced, with Windows contributing nothing.

4 · WASAPI exclusive mode — the intercept

WASAPI has a second path: exclusive mode. An app that opens a capture device exclusively owns that device. The samples flow straight from the ADC to the app with the audio engine bypassed — no level multiply, no enhancements, no resampling. This is exactly what we want, and it is the entire point of what the product calls the "intercept."

Exclusive mode has three preconditions, and getting all three right on a real machine is the subject of the rest of this document:

  1. The Windows checkbox "Allow applications to take exclusive control of this device" must be ticked (Recording → device → Properties → Advanced). This is a one‑time operator step.
  2. You must open the device's WASAPI instance — not one of its other operating‑system instances (§5.1).
  3. You must request a format and buffer size the hardware supports exactly, because exclusive mode does no conversion of any kind (§5.2).

5 · The saga — four bugs between "we wrote exclusive" and "exclusive engaged"

The receiver's capture code asked for exclusive mode from the start (sounddevice.WasapiSettings(exclusive=True)). On the developer's bench it appeared to work. On the operator's machine it silently fell back to shared every time — and because the fallback is silent, nothing looked broken except the one behavioral tell (the volume slider still changed the decode). Four distinct faults had to be cleared.

5.1 · Bug one — opening the wrong instance of the card PaErrorCode −9984

Windows exposes each physical sound card once per host API. A host API is a driver family — Windows has four: MME (oldest), DirectSound, WASAPI, and WDM‑KS. So one USB sound card enumerates as four separate "devices." On the operator's machine the single UFO202‑class card appeared as:

IndexHost APIChannelsRateName as reported
1MME244100Microphone (2- USB Audio CODEC (truncated)
7DirectSound244100Microphone (2- USB Audio CODEC )
15WASAPI148000Microphone (2- USB Audio CODEC )
23WDM‑KS244100Microphone (USB Audio CODEC)

Exclusive mode is a WASAPI concept. The WasapiSettings object is WASAPI‑specific stream information. If you attach it to a device whose host API is not WASAPI — say the MME instance at index 1 — PortAudio (the cross‑platform audio library under sounddevice) rejects the combination with error −9984, paIncompatibleHostApiSpecificStreamInfo — "you handed WASAPI settings to a non‑WASAPI device." The receiver caught that error and quietly fell back to shared.

So the first requirement is to find and open index 15 specifically. The code now queries the host‑API list, finds the WASAPI one, and ranks the WASAPI instances of the card first.

5.2 · Bug two — a buffer size the hardware didn't allow AUDCLNT_E_BUFFER_SIZE_NOT_ALIGNED

Even on the correct WASAPI device, a second fault remained. Shared mode will re‑block audio into whatever chunk size you ask for; exclusive mode will not. In exclusive mode the application's buffer must align to the device's hardware period. The receiver was forcing a fixed blocksize = 2048 frames. When that doesn't match the device's aligned period, the low‑level IAudioClient::Initialize call fails with AUDCLNT_E_BUFFER_SIZE_NOT_ALIGNED, which surfaces as yet another exception — and again, silent fallback to shared.

This was the subtle one, because it was invisible in isolation: the diagnostic self‑check captured with sounddevice.rec(), which leaves the block size unspecified (0) and lets WASAPI choose the device‑aligned buffer — so the self‑check got exclusive while the receiver, forcing 2048, did not. The two differed by exactly one argument.

Fix: open the capture stream with blocksize = 0 and let WASAPI pick the hardware‑aligned period (~10 ms blocks). The decoder's callback already accepts any block length, so nothing downstream cares. The bounded capture queue was re‑sized for the smaller native blocks so its backlog stays correct and memory stays bounded.

5.3 · Bug three — the launcher was choosing the wrong instance for us

With the two fixes above, the auto‑selection path chose index 15 correctly. But the receiver is normally started by its one‑window launcher, which has a "Radio input" dropdown and passes the chosen device to the decoder as --device=N. That dropdown lists every instance of the card (indices 1, 7, 15, 23 all named almost identically), and its default was the first match — the MME copy, index 1. So the launcher was explicitly forcing the one device that cannot do exclusive, overriding the auto‑selection, and we were back to −9984.

The robust fix is to make the receiver resolve whatever device it is handed to that card's WASAPI twin before opening — whether the index came from the launcher, from auto‑detect, or from a manual prompt. Given a chosen device, it finds the WASAPI‑host‑API input that belongs to the same physical card and uses that instead.

Name‑matching gotcha: you cannot match the twin by exact name. MME truncates device names to 31 characters, so the MME instance reads …USB Audio CODEC (trailing space, no closing parenthesis) while the WASAPI instance reads …USB Audio CODEC ). The resolver therefore normalizes both names to alphanumerics only (microphone2usbaudiocodec) and matches on a prefix, which survives the truncation and the punctuation difference.

5.4 · The gotcha that hid everything — a buffered log

Through much of the hunt the decoder log looked empty, which made it impossible to see whether exclusive had engaged. The cause was unrelated to audio: when the launcher redirects the decoder's output to decoder_log.txt, Windows block‑buffers stdout (it only flushes in large chunks when output isn't a console). So the status line audio capture: EXCLUSIVE/shared mode — an ordinary print() — sat in a buffer and never reached the file, while Python warnings (which go to stderr, unbuffered) were the only thing that ever appeared. Reconfiguring stdout/stderr to line‑buffered at startup made the log live, and the truth became visible immediately.

6 · The method that cracked it — isolate before you integrate

The decisive move, at the operator's insistence, was to stop testing through the full program and write a tiny direct probe that did one thing: enumerate every input device with its host API, then try to open the card's WASAPI instance in exclusive mode and print exactly what happened, at 1 and 2 channels, via both a callback stream and rec(). One run turned four invisible silent fallbacks into one readable table:

idx 15  [Windows WASAPI]  'Microphone (2- USB Audio CODEC )'
      InputStream  ch1 @ 48000Hz:  EXCLUSIVE OK
      InputStream  ch2 @ 48000Hz:  FAIL -- Invalid number of channels [-9998]
idx 1   [MME]  ...   FAIL -- Incompatible host API specific stream info [-9984]
idx 7   [DirectSound] ... FAIL -- -9984
idx 23  [WDM-KS] ...      FAIL -- -9984

That single table named the winning recipe unambiguously — index 15, WASAPI, one channel, 48 kHz, callback stream — and proved the other three instances could never work. Everything after was mechanical. The lesson is general: when a feature fails silently inside a large program, reproduce it in the smallest possible standalone script first; the error you can't see in the product is usually plainly printed by ten lines in isolation.

7 · The final working recipe

  1. Select a device (launcher dropdown, auto‑detect, or prompt). Any instance of the card is acceptable as input here.
  2. Resolve to the WASAPI twin — find the WASAPI‑host‑API input belonging to the same physical card (normalized‑prefix name match, truncation‑safe).
  3. Open exclusive with a native format — WasapiSettings(exclusive=True), dtype=int16, blocksize=0 (device‑aligned), trying 1 channel then 2.
  4. Fall back to shared only if exclusive genuinely cannot open, and say so in the log. (Shared still decodes correctly — see §2 — it just re‑exposes the level slider.)
dev, name = pick_device(sd, forced)          # launcher --device, auto, or prompt
dev, name = _resolve_wasapi(sd, dev, name)   # -> the card's WASAPI instance
es = sd.WasapiSettings(exclusive=True)
stream = sd.InputStream(device=dev, channels=1, samplerate=48000,
                        blocksize=0, dtype="int16", callback=cb,
                        extra_settings=es)   # EXCLUSIVE 1ch @ 48000

8 · How you know it is working

  • The log. With line‑buffered output, decoder_log.txt prints .. audio capture: EXCLUSIVE 1ch mode and listening on: Microphone (2- USB Audio CODEC ) — note the closing parenthesis, which identifies the WASAPI instance rather than the truncated MME name.
  • The volume‑slider test (definitive). With the receiver running, set the Windows microphone Level to 100%. In shared mode this drives the hiss into clipping and the decode stalls; in exclusive mode it has no effect at all, because the slider is out of the path. Confirmed on the bench: at Level 100 the fleet kept plotting without a hiccup.

9 · The one‑click self‑check

The package ships a Troubleshooting/ folder with a one‑click self‑check that inspects the whole chain and prints PASS / WARN / FAIL per piece: Python, the package files, the required libraries, internet reach (only needed for the one‑time install, with an offer to fetch missing libraries), the decode engine import, a one‑second live audio reading (silent → cable; clipping → too hot; ~55–65% peak → the open‑squelch hiss, good — and it reports whether it got EXCLUSIVE or shared, and why), the GPS, and the network ports. It uses the same WASAPI‑instance selection described here, so it is also a quick way to confirm the card can do exclusive before the receiver is even started.

10 · Glossary

ADC (analog‑to‑digital converter)
The chip in the sound card that turns the radio's analog baseband into 16‑bit numbers. Exclusive mode delivers these untouched.
WASAPI
Windows Audio Session API — the modern Windows audio interface. Has two modes: shared (through the mixer) and exclusive (direct to hardware).
Shared mode
The default. Windows mixes, levels, and may "enhance" the audio before your app sees it. Exposes the volume slider.
Exclusive mode
Your app owns the device; samples flow straight from the ADC with the Windows engine bypassed. No level, no effects, no resampling.
Host API
A Windows audio driver family: MME, DirectSound, WASAPI, or WDM‑KS. One physical card appears once under each, so it looks like four devices.
PortAudio / sounddevice
PortAudio is the cross‑platform C audio library; sounddevice is the Python wrapper the receiver uses to open streams.
blocksize
How many audio frames per callback. In exclusive mode it must align to the hardware period; passing 0 lets WASAPI choose a valid size.
BER (bit error rate)
The fraction of decoded symbols that are wrong. Set by RF signal‑to‑noise, not by audio level — until the level clips.
FM quieting
The effect that makes a received signal reduce the FM receiver's noise; it is why a C4FM packet reads lower than the between‑transmission hiss (~3:1).
−9984 / −9998
PortAudio errors seen here: −9984 = WASAPI settings on a non‑WASAPI device; −9998 = a channel count the device doesn't support in exclusive mode.
